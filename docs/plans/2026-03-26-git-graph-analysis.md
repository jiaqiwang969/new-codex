# Git Graph Analysis

**Date:** 2026-03-26
**Scope:** local `git-graph` workbench feature in the upstream-merge branch

## Summary

`git-graph` is not a small TUI-only enhancement. The current branch vendors an
entire third-party workspace crate and only uses a narrow slice of it to power a
single `Ctrl+G` overlay in the TUI.

That means the real merge decision is not "can this be reattached?" It can. The
real question is whether the feature is valuable enough to justify carrying:

- a full extra workspace member
- lockfile churn
- Bazel lock updates
- a third-party codebase whose CLI/docs/workflows mostly are not used by Codex

## Current Integration Shape

**Primary files**

- `codex-rs/git-graph/**`
- `codex-rs/tui/src/git_graph_widget.rs`
- `codex-rs/tui/src/app.rs`
- `codex-rs/Cargo.toml`
- `codex-rs/tui/Cargo.toml`
- `codex-rs/Cargo.lock`
- `MODULE.bazel.lock`

**User-facing behavior**

- `Ctrl+G` opens a git-graph overlay from `app.rs`
- the overlay is generated by `git_graph_widget.rs`
- the overlay tries the embedded `git-graph` library first
- if that fails, it falls back to `git log --graph` and converts ASCII line art
  into a Unicode-looking display

## What The TUI Actually Uses

The TUI integration uses:

- repo opening
- graph construction
- unicode rendering helpers
- branching model lookup from `git-graph.toml`

It does **not** need most of the vendored project surface:

- standalone CLI
- release workflows
- docs/manual bundle
- separate crate lockfile for standalone development

So the local branch is currently carrying far more than the TUI feature itself
strictly requires.

## Dependency Footprint

Compared to `upstream/main`, this feature adds:

- workspace member `git-graph`
- `git-graph = { path = "git-graph" }` in workspace dependencies
- `git-graph = { workspace = true }` in `codex-tui`
- large `Cargo.lock` delta
- `MODULE.bazel.lock` delta
- a full vendored source tree, docs, workflows, and its own `Cargo.lock`

This makes `git-graph` the heaviest dependency decision inside Block 7.

## Runtime Integration Risk

The runtime integration risk is actually modest.

The TUI hook itself is small:

- one `Ctrl+G` keybinding in `app.rs`
- one overlay creation call into `git_graph_widget.rs`

So once the dependency decision is accepted, the reattachment work is easy.

## Test Coverage Reality

Current targeted test pass:

- `cargo test -p codex-tui git_graph -- --nocapture`

Result:

- no dedicated TUI tests matched

Implication:

- there is no focused regression test coverage for this feature in the current
  branch
- the safety argument for keeping it is mostly manual-value-based, not
  test-backed

## Merge Recommendation

Treat `git-graph` as a standalone optional sub-block, separate from the rest of
Block 7.

### If keeping it

- keep it isolated from other TUI merge work
- preserve the tiny app/widget hook surface
- accept that the branch intentionally carries a third-party vendored crate

### If trimming it later

There are two plausible lighter future directions:

1. keep the feature but rely only on the `git log --graph` fallback path
2. extract only the library pieces actually needed for the TUI instead of
   carrying the full upstream project layout

Neither of those lighter paths is required for the current upstream merge, but
both are cleaner than silently carrying the entire vendor tree forever without
acknowledging the cost.

## Practical Conclusion

`git-graph` is easy to preserve technically and expensive to preserve
organizationally.

So the right merge stance is:

- do not let it block the upstream merge
- do not mix it with `session_bar` or `ralph-loop`
- keep it only as an explicit, conscious dependency choice
